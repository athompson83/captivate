## Required User Actions

- **Set the Stripe statement descriptor.** The account object read on 2026-09-03 carries a business name already — `business_profile.name` is "Captivate" and the dashboard display name is "Axtevi" — but the thing that actually appears on a card statement is `settings.payments.statement_descriptor`, and it reads **"ADAM THOMPSON"** with the card prefix "ADAM". A subscriber's bank line would name a person rather than the product they bought, which is the usual cause of a chargeback for an unrecognised charge.
- **Set the Supabase Auth URL configuration for production** — Authentication → URL Configuration: Site URL `https://www.axtevi.com`, and `https://www.axtevi.com/auth/callback` (or `https://www.axtevi.com/**`) under Redirect URLs. Today the allowlist does not include it, so GoTrue silently substitutes the default Site URL: a sign-up confirmation and a password-recovery email requested through the production project on 2026-09-02 both carried `redirect_to=http://localhost:3000`. Every real sign-up confirmation and password reset is sending people to a machine that is not there. This is a dashboard setting; the agent has no management token, and nothing in the code can substitute for it.
- **The image key and `PEXELS_API_KEY` are both set**, and neither is an action any more. Read from a signed-in production session on 2026-09-02 rather than inferred: the asset picker offered a **Find** tab, which renders only when `isStockSearchConfigured()` is true, and a **Generate** tab, which renders only when `isImageGenerationConfigured()` is true — then generated a real picture. Which gateway serves images was settled a day later, when the fixed accept path wrote an `assets` row on production carrying `provider = 'openai'`: that column records the resolved `IMAGE_PROVIDER`, not a model string, so production's images go through **OpenAI** and the OpenRouter account's exhausted balance cannot affect them.
- Supply the brand assets as files in the repository (`public/`), rather than as images in conversation. The wordmark component is in place and the palette is the mark's, but the tile is still a placeholder glyph and the favicon and share card are unchanged.
- Confirm `STRIPE_WEBHOOK_SECRET` is the signing secret of the endpoint matching the mode of `STRIPE_SECRET_KEY`. Test and live endpoints have different secrets, and a mismatch fails every delivery while everything else looks correct.
- Delete the two disposable `webhook-probe@example.com` customers left by the end-to-end proof (tagged `delete_me`), and the live-mode customer `cus_VBdTRnSdxlyuQ1` (email `captivate-e2e-1788362743@mail.proviciency.com`) that the 2026-09-02 checkout probe created; the MCP in use cannot delete customers. The Supabase side is already gone: on 2026-09-03 the disposable identity was removed from production in full — four generated images deleted through the product's own `deleteAsset` path so the storage objects went with the rows, then its 27 decks, 5 `ai_generations` rows, 2 `lecture_notes` rows, its `billing_customers` row and the `auth.users` record. Production now holds two accounts and 15 decks, 14 of them the Product Owner's, and no object under the disposable prefix. - Open the deck titled **"AI in the Classroom: Buying Back Time for What Matters — rebuilt copy (review before use)"** and decide whether it replaces the original. The original's nine empty statement scenes were produced before PR #44 fixed the composer; the copy carries the same scenes with each statement drawn as its centred heading, and nothing else changed. Before public launch the owner still needs to: enable leaked-password protection in the Supabase dashboard (Auth → Policies — dashboard-only, no management token available to the agent); set `NEXT_PUBLIC_SUPPORT_EMAIL` in Vercel so the legal pages can name a real address; decide email policy and provider; review the privacy and terms wording, whose facts are code-derived but which has had no legal review; and accept the release as shipped/live.

One of those decisions is not a preference but a gap. `docs/SECURITY.md` records that there is **no account-deletion flow**: the cascading deletes exist in the database, and nothing in the UI reaches them, so removing an account is done by hand. The privacy page says so plainly rather than implying a button exists. Whether that is acceptable at launch or blocks it is the owner's call and has **not been made**; it is recorded here rather than left implicit, because a gap nobody decided about is indistinguishable from one nobody noticed.

None of these blocks current engineering.
